# 2026-11-24 — B2.2 Source-Adaptive Chroma candidate

## Baseline and scope
User reports actual playback with new B2.1 feels good and more suitable than A. Treat B2.1 Adaptive Luma as the user-preferred baseline; do not retune or replace the SVDLUT graph, B1, A, B2.1 estimator, input/dither pipeline, MFG or depth. The new incremental overlay is against the **B21 Adaptive Luma incremental package already applied**. This is an optional candidate, not an accepted replacement of all legacy color strategies.

## Research and implementation
- ACES 2.0 chroma compression and rational knee: https://docs.acescentral.com/system-components/output-transforms/technical-details/chroma-compression/ and https://docs.acescentral.com/system-components/output-transforms/technical-details/gamut-compression/
- W3C perceptual gamut mapping: https://www.w3.org/TR/css-color-4/#gamut-mapping
- These support separating tone/color and using continuous color compression. They do NOT validate this source-relative code-space operator or its parameters. No claim of ACES/JMh/OKLCh equivalence, perceptual constant hue or perceptual JND.
- Existing B2.2/R1 mix memory-color heuristics with boundary compression; R1 only constrains gamut radius, not arbitrary in-gamut shifts. Candidate instead limits the displacement from original chroma at B2.1 output Y'. Compute source chroma sc = source - Y'(source), fit it along its ray into RGB at target Y'(B2.1 candidate), then use that as anchor. Candidate and anchor are in gamut at identical Y'. Let d = max(abs(candidate-anchor)), L = 2/255 + 1.5*max(abs(sc)), knee=.65*L. For d<=knee return candidate unchanged, else map d to knee + (L-knee)*(d-knee)/(L-knee+d-knee), and scale the displacement vector by mapped/d. Both endpoints legal and convex blend preserves code-luma; no channel-specific clipping except floating point guard. This constrains displacement, not absolute saturation or hue angle independently. It cannot guarantee preservation of colored gradient, perceptual lightness or intentional white balance; this is for optional evaluation.
- Candidate is enabled only for Temporal B + B2.1 + B2.2 with R1 and M1 off. B2.2 unchecked leaves B2.1 as-is. B2.1 off: legacy B2.2 memory/gamut behavior remains when P1 off; R1 and M1 legacy paths remain unchanged. P1 has existing precedence over old B2.2/R1/M1; when candidate selected P1 now applies the same B2.2 helper after B2.1 and before independent P1 adjustments, which can themselves alter color/luma. Same CB layout, existing reserved Enhancements.w used, no setting IDs or registry changes. Label B2.2: Chroma, updated tooltip. No added GPU pass, readback, model or buffer; actual GPU overhead not measured. No runtime dependencies. No commit/deployment.

## Validation
- `python build-support/edition/tests/SvdLutAdaptiveChromaModel.py GRAPH [IMAGES ...]` uses actual graph, original packing and existing B2.1 CPU estimator, builds the actual scalar HLSL helper extracted as C++ (not a real D3D shader compiler) and compares it with vector math. Requires developer g++, torch, numpy, PIL, skimage; not renderer runtime. Earlier B21 model script made importable; CLI unchanged.
- 100,000 random composition cases, 256 neutral cases, 4097 fixed-ray monotonic probes passed. Max random Y' error 0.0000304 of one 8-bit code. B21 existing 100,000 tests and 30 x 4 x 256 gradient probes passed unchanged. Actual seven source images at 256x256, full B strength, still frames not temporal blend. CPU reference model, not Windows DirectML. All 458,752 image pixels checked scalar/vector; max difference 0.000061 code; max Y' change <= 0.000023 code before output quantization. Raw data adjacent JSONL. Natural image average chroma delta retention: astronaut 100%, coffee 100%, chelsea 98.77%, rocket 93.32%. Neutral pixel average chroma magnitude in three cards: 1.110 -> .687, .985 -> .725, .182 -> .141 code. Not proof of subjective picture quality. Parameter sweep 10 options favored 2/255 + 1.5*source radius for low neutral cast and retained natural color delta; engineering screening, no standardized thresholds. R1/M1 and P1 actual playback not validated.
- No Windows toolchain, pwsh, Direct3D runtime here; x64 Release, actual D3DCompile/reflection test, page tests, real GPU cost, full-resolution temporal and color-gradient tests pending. Do not report those as passed. Original model vs PyTorch checkpoint and native VP prescale/earlier quantization remain separate outstanding reference pipeline questions.

## Acceptance and rollback
For isolated candidate: Temporal B1, B2.1 checked, R1/M1 off, Preferred/Skin off initially, compare B2.2 unchecked/checked at same B strength. Prefer normal films and title cards, retain creative color intent; check buffer and flicker. B2.2 off immediately restores preferred B2.1 baseline. Test P1 separately; old R1/M1 kept as controls, not combined with candidate. No need to replace model. If this does not improve subjective result, retain B2.1 rather than adding more heuristics. Do not confuse mean chroma retention with quality score. Further independent hue/chroma controls, colored gradients and temporal stability require evidence first.
